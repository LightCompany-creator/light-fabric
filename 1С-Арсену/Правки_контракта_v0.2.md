## 1. Материалы привязаны к продукции

**Было (6.8):** `"materials": [ { "item_id": "…", "qty": 268.8 } ]`.

**Стало:**

```json
"materials": [
  { "item_id": "…", "product_id": "…", "qty": 268.8 }
]
```

`product_id` обязателен и должен совпадать с одним из `product_id` в `products` той же смены.
Строка без него или с продукцией, которой нет в `products`, — `400 validation`, в `details`
номер строки.

**Почему.** В 1С у строки материалов в «Отчёте производства за смену» продукция — обязательное
поле (проверка при проведении), и номенклатурная группа материала должна совпадать с группой
продукции. Без привязки 1С не знает, на что списать материал, если в смене два и более продукта.
Распределять «по нормам» на стороне 1С не будем — это расчётная, а не фактическая разбивка.

Пустые `materials` — по-прежнему допустимы: 1С сама заполнит их по основной спецификации
продукции (норма × выпуск), продукция при этом проставится автоматически.

## 2. Виды работ без продукции вместо «простоя»

**Было (6.3):** `"is_downtime": true/false` у `work_types[]`; простой — единственный вид работ без
продукции.

**Стало:**

```json
"work_types": [
  { "id": "…", "code": "…", "name": "Литьё 6-парка", "unit": "пар", "requires_product": true },
  { "id": "…", "code": "…", "name": "Простой",       "unit": "ч",   "requires_product": false },
  { "id": "…", "code": "…", "name": "Чистка форм",   "unit": "ч",   "requires_product": false }
]
```

Правило для `outputs` (6.8): `product_id` обязателен, если у вида работ `requires_product = true`;
для остальных — `null`. Признак ведётся в 1С в справочнике видов работ.

**Почему.** По данным 1С фабрика уже оплачивает работы без продукции (чистка форм, погрузка,
уборка в цехе «Коврики»), и делает это отдельным документом на общепроизводственные расходы,
а не через отчёт производства. Простой — такой же случай. При закрытии смены 1С делает так же:
строки с продукцией → «Отчёт производства за смену», строки без продукции → документ начисления
ЗП на 25 счёт. Для приложения разницы нет — это одна смена и один `close`.

## 3. Закрытие смены двухшаговое

**Было (3.2, 6.9):** `close` создаёт и проводит ОПЗС; при любой ошибке ничего не записывается,
смена остаётся `open`, причина в ответе.

**Проблема.** Часть ошибок при проведении — не про ввод начальника цеха, а про учёт: нет материала
на складе цеха, закрытый период, не заведена расценка на вид работ, не заполнена статья затрат
у подразделения. Смена заканчивается ночью, бухгалтерии нет, планшет показывает «нельзя закрыть».

**Стало.** Закрытие — два шага с разными владельцами:

1. **Закрытие смены** (`POST /shifts/{id}/close`). 1С проверяет только ввод цеха: сотрудники,
   виды работ и продукция принадлежат цеху; у строк выработки с `requires_product` есть
   продукция; у материалов указана продукция. Если ввод корректен — смена становится `closed`
   и больше не редактируется. Это не может упасть по бухгалтерским причинам.
2. **Отражение в учёте.** Сразу после шага 1 1С пытается создать и провести учётные документы
   (ОПЗС и, если есть строки без продукции, начисление ЗП). Если получилось — `accounting.status
   = "done"`. Если нет — смена остаётся `closed`, причина сохраняется в 1С, `accounting.status =
   "pending"`; бухгалтер утром устраняет причину и повторяет отражение из 1С. Приложению для
   этого ничего делать не нужно.

Жизненный цикл (3.2):

```
POST /shifts ──► open ──(PUT …)──► POST /shifts/{id}/close
                                        │
                    ввод некорректен: 400 validation, смена остаётся open ◄──┤
                    ввод корректен: closed ──► accounting: done | pending ◄──┘
                 reopen (только администратор) ◄── closed
```

Ответ `close` (6.9), успех отражения:

```json
{ "ok": true,
  "shift": { "id": "…", "status": "closed", "closed_at": "2026-09-13T22:40:00", "version": "…" },
  "accounting": {
    "status": "done",
    "message": "",
    "documents": {
      "production_report": { "id": "…", "number": "0000-012345", "date": "2026-09-13" },
      "payroll": null
    }
  },
  "warnings": [ "Материалы заполнены по спецификации: 3 позиции" ] }
```

Отражение не удалось (смена всё равно `closed`):

```json
{ "ok": true,
  "shift": { "id": "…", "status": "closed", "closed_at": "…", "version": "…" },
  "accounting": {
    "status": "pending",
    "message": "Недостаточно остатка: Пластикат ЭВА чёрный — доступно 120 кг, требуется 140 кг",
    "documents": { "production_report": null, "payroll": null }
  } }
```

Тот же блок `accounting` отдаётся в `GET /shifts/{id}` (6.6) и в кратком виде в списке
`GET /shifts` (6.5): поле `accounting_status: "done" | "pending"` вместо `production_report`.
Повторный `close` по уже закрытой смене — `200` с текущим состоянием (в том числе с актуальным
`accounting`), это штатный способ «обновить» статус учёта.

Ошибки ввода по-прежнему блокируют: `400 validation` с `details` по строкам, смена остаётся
`open`. Коды `insufficient_stock`, `period_closed`, `posting_failed` из таблицы 5.6 в ответе
`close` больше не возвращаются — их текст приходит в `accounting.message`. Для `confirm`
перемещения `insufficient_stock` остаётся как был.

**Что показать пользователю.** `pending` — не ошибка цеха. Достаточно пометки «смена закрыта,
ждёт отражения в учёте» и текста `message` по запросу. Открывать смену заново для исправления
не нужно и нельзя.

## 4. Ключ идемпотентности только для перемещений

**Было (5.4):** `Idempotency-Key` для `POST /transfers` и `POST …/close`.

**Стало:** только для `POST /transfers`. Для `close` ключ не нужен: повтор по закрытой смене
возвращает её текущее состояние (см. п. 3), дубль невозможен по построению. Заголовок в `close`
допускается и игнорируется.

## 5. Как приложение должно формировать ключ

Защита от дублей работает только при таких условиях (5.4, дополнение):

- ключ создаётся в момент, когда пользователь нажал «отправить», **до первой попытки** запроса;
- хранится в офлайн-очереди вместе с действием и **не меняется** при повторных попытках;
- передаётся в заголовке `Idempotency-Key` **при каждой попытке, включая первую**;
- формат — любая строка до 36 символов, уникальная в пределах приложения (UUID не обязателен;
  текущий формат очереди `<timestamp>-<random>` подходит).

Поведение 1С: если перемещение с таким ключом уже есть — возвращается оно, в текущем состоянии
(возможно, уже подтверждённое получателем), с кодом `200`, а не `201`. Если документ с этим
ключом был удалён через `DELETE`, повтор создаст новый.

Замечание по текущему прототипу: очередь в `lib/offline-queue.ts` уже даёт действию стабильный
`id` — его и использовать как ключ; но сейчас первая (онлайновая) попытка идёт мимо очереди и
идентификатора не получает — это нужно поменять, иначе потерянный ответ на первую попытку даст
дубль.

## 6. Уточнение принципа

Пункт 1, «1С — единственный судья»: 1С отклоняет **некорректный ввод** (`validation`,
`forbidden`, `state`, `conflict`). Корректность **учёта** (остатки, период, расценки, статьи)
проверяется на шаге отражения и не блокирует работу цеха — это зона бухгалтерии в 1С.

## 7. Уточнения по сменам по итогам реализации (22.09.2026)

Найдено при реализации операций смен в 1С; поведение уже такое, контракт приводится в соответствие.

- **`comment` в теле `close` (6.9) не обрабатывается.** Комментарий смены передаётся только через `PUT /shifts/{id}` до закрытия. Тело `close` может быть пустым.
- **Повторный `close` по закрытой смене** (штатный способ обновить блок `accounting`, п. 3 этих правок) отправлять **без `If-Match`**: проверка версии выполняется до ветки «уже закрыта», и устаревшая версия даст `409 conflict`.
- **`version` меняется при `close` дважды** (проведение смены и запись ссылок на документы учёта). Приложению всегда брать `version` из последнего ответа (`close`, `GET`), а не хранить значение после `PUT`.
- **Одна ошибка `validation` содержит все нарушения** тела `PUT` в `details[]` (`section`, `row`, `field`, `message`); `message` верхнего уровня — первая деталь. Приложение может подсветить все строки сразу.
- `shift_no` — только число 1 или 2; `date` — `ГГГГ-ММ-ДД` (время, если передано, отбрасывается).
- Некорректный GUID в `{id}` → `404 not_found` (как «смена не найдена»), не `400`.

## 8. Ответы без JSON-тела (22.09.2026)

Проверено на опубликованной базе. Часть ошибок отдаёт не наш код, а платформа 1С или веб-сервер, и у них **нет JSON-тела**:

- `401 Unauthorized` — неверный логин или пароль (заголовок `WWW-Authenticate: Basic realm="1C:Enterprise 8.3"`, тело HTML от IIS).
- `403 Forbidden` с текстом «Недостаточно прав для использования ресурса с данным HTTP методом» — у пользователя нет права на метод сервиса (например, `POST /shifts/{id}/reopen` для начальника цеха). Тело — plain text, не JSON.
- `404 Not Found` с HTML от IIS — неизвестный путь вне шаблонов сервиса (например `/v1/nope`).

Приложение должно обрабатывать такие ответы по коду HTTP, не пытаясь разобрать тело как JSON. Логин в Basic Auth кодируется в **UTF-8** (кириллица допустима, но cp1251 даёт 401).

## Что не меняется

Модель данных (раздел 2), маршруты и методы (раздел 6), перемещения (раздел 4, 6.11–6.16),
версии и `If-Match` (5.5), кэш (5.7), список открытых вопросов В-1…В-5 (раздел 8). Вопрос В-1
(материалы на складе цеха) перестал быть блокирующим для цеха, но остаётся важным: если
материалов на складах цехов не будет, все смены будут уходить в `pending`, и бухгалтерии
придётся разбирать их каждое утро.
