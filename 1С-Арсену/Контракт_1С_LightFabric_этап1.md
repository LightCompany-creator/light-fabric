# Контракт обмена 1С ↔ LightFabric. Этап 1: отчёт начальника цеха и перемещения

> Версия 0.1 от 13.09.2026 — черновик к обсуждению. Заменяет `API_1C_Endpoints.md`,
> `ТЗ_LightFabric.md` (раздел 6) и `Вопросы_1С_программистам.md` в части обмена —
> они описывали старую модель (своя база + синхронизация).
> От: Арсен (1С). Для: Наира / команда LightFabric.
>
> Цель документа — дать приложению всё, чтобы работать параллельно с доработкой 1С:
> модель данных, жизненный цикл документов, точный состав запросов и ответов.
> Имена полей и маршрутов — окончательные, если в обсуждении не решим иначе.

## 1. Модель работы — коротко

- **1С — единственная база данных и единственный сервер.** У приложения нет своей БД
  и сервера; оно хранит только кэш сеанса на планшете.
- **Каждый пользователь приложения — пользователь 1С** (Basic Auth). 1С сама знает, какие
  цеха ему доступны, и фиксирует его в документах как ответственного. Заводит пользователей
  администратор 1С.
- **Один запрос на сценарий.** При входе в цех приложение одним запросом получает всё для
  работы смены (сотрудники, виды работ, продукция, материалы, остатки, открытые смены).
  Дальше работа идёт с кэшем; в 1С уходят только изменения документов.
- **Документы живут в 1С с момента создания.** Открытие смены создаёт в 1С черновик;
  строки дописываются по мере ввода; закрытие смены — проведение. Поэтому история, второй
  планшет, бухгалтер в 1С — все видят одно и то же.
- **1С — единственный судья.** Любая запись может быть отклонена (нет остатка, нет прав,
  закрытый период). Приложение показывает причину из ответа и даёт исправить.
- **Денег в приложении нет.** Расценки и суммы ЗП приложению не отдаются; начисление
  считается в 1С при закрытии смены.

### Роли этапа 1

| Роль | Что делает в приложении | Как выглядит в 1С |
|---|---|---|
| Начальник цеха | открывает/ведёт/закрывает смены своего цеха; создаёт перемещения из своего цеха; подтверждает входящие перемещения | пользователь 1С, ответственный за склад цеха (регистр «Ответственные лица складов») |
| Склад готовой продукции (Рома) | подтверждает входящие перемещения | то же — цех «Склад ГП» со своим складом |
| Администратор | переоткрывает закрытые документы, снимает подтверждения | полноправный пользователь 1С |

Начальник производства, коммерческий отдел, заказы — этап 2, здесь не рассматриваются.
В документе смены зарезервировано поле `task_id` под задание на смену.

## 2. Справочная модель: что такое «цех» в 1С

| Понятие LightFabric | Объект 1С | Как связано | Кто ведёт |
|---|---|---|---|
| Цех (`workshops`) | Подразделение организации (группы «Производство обуви», «Коврики»…) | — | уже заведены |
| Склад цеха | Склад | **новая привязка «цех → склад»** в 1С, ровно один склад на цех | администратор 1С по списку от фабрики |
| Работники цеха (`employees`) | Сотрудники | **новый регистр «сотрудники подразделений производства»**; один сотрудник может быть в нескольких цехах | кадры/Наира в 1С |
| Вид работ / операция (`rates.operation`) | Виды работ производства | регистр «виды работ подразделений» — уже есть и заполнен | технолог в 1С |
| Расценка (`rates.rate_per_unit`) | регистр «стоимость видов работ» по цеху и дате | уже есть и заполнен; **приложению не отдаётся** | бухгалтерия |
| Продукция цеха (`articles`) | Номенклатура | регистр «продукция подразделений» — уже есть и заполнен | технолог в 1С |
| Материалы цеха (`materials`) | Номенклатура | комплектующие основных спецификаций продукции цеха + всё, что есть на остатке склада цеха | — |
| Нормы расхода (`norms`) | Спецификации номенклатуры | основная спецификация продукции | технолог в 1С |
| Пользователь | Пользователь 1С | ответственный за склад цеха → доступ к цеху | администратор 1С |

Ключ любого объекта — **`id` (GUID ссылки 1С)**. У справочников дополнительно отдаётся
`code` (код 1С) и `name`. Приложение хранит `id` и передаёт его во всех запросах.
Коды нужны только для отображения и сверок.

Справочники приложение **не синхронизирует и не хранит постоянно** — получает контекст цеха
при входе (п. 6.3) и обновляет по кнопке или по таймеру (достаточно раз в смену).

## 3. Процесс «смена»

### 3.1 Документ в 1С

Новый документ **«Отчёт начальника цеха»** — не бухгалтерский, хранит ровно то, что
ввели на планшете. Шапка: организация, цех, склад цеха, дата, номер смены, статус,
ответственный (пользователь), комментарий, ссылка на созданный ОПЗС, `task_id` (резерв).
Табличные части:

- **Состав смены** — кто вышел: сотрудник, основной вид работ.
- **Выработка** — сотрудник × вид работ × продукция × количество (+ брак). Это и есть
  сделка: одна строка = одно начисление. Распределять ничего не нужно — количество на
  каждого работника вводится явно. Простой — тоже строка выработки с видом работ
  «Простой» (заводится в 1С на цех) и количеством в часах.
- **Продукция** — итог выпуска по продукции: изготовлено, брак. Заполняется приложением
  (может быть суммой выработки по «выпускающему» виду работ, может вводиться отдельно —
  решает приложение; 1С берёт как есть).
- **Материалы** — номенклатура, количество по факту. Если таблица пустая — 1С при закрытии
  заполнит её сама по основной спецификации продукции (норма × выпуск).
- **Комментарии/события** — свободный текст (необязательно).

### 3.2 Жизненный цикл

```
POST /shifts  ──►  open  ──(PUT /shifts/{id} сколько угодно раз)──►  POST /shifts/{id}/close
                                                                          │
                              ok: closed, создан и проведён ОПЗС ◄────────┤
                              error: остаётся open, причина в ответе ◄────┘
                 reopen (только администратор) ◄── closed
```

- **Открытие** (`POST /shifts`): цех, дата, номер смены (1 или 2). Если такая смена уже
  открыта — 1С вернёт её, а не создаст вторую (идемпотентно). Ответ содержит `id` документа.
- **Ведение** (`PUT /shifts/{id}`): приложение присылает **полное текущее состояние**
  документа (все таблицы целиком). 1С заменяет содержимое. Так проще и надёжнее, чем
  дописывать по строке: офлайн-очередь может повторять запрос сколько угодно раз, порядок
  не важен, результат одинаковый. Документ не проводится, движений нет.
- **Закрытие** (`POST /shifts/{id}/close`): 1С проверяет документ, создаёт штатный
  «Отчёт производства за смену» (ОПЗС) и проводит его: приход продукции на склад цеха,
  списание материалов со склада цеха, начисление сдельной ЗП по видам работ с расценками
  на дату смены. При любой ошибке ничего не записывается, смена остаётся `open`,
  в ответе — причина (см. 5.6). После успеха документ `closed`, `PUT` запрещён.
- **Переоткрытие** (`POST /shifts/{id}/reopen`): только администратор. ОПЗС
  распроводится и помечается на удаление, смена снова `open`.
- Вторая смена того же дня — отдельный документ (`shift_no: 2`). Несколько ОПЗС в день на
  цех для 1С норма (сейчас по некоторым цехам их до 7 в день).

### 3.3 Что приложение НЕ делает

- Не считает ЗП и не показывает расценки.
- Не списывает материалы и не ведёт остатки само — только показывает остатки из 1С.
- Не хранит закрытые смены — история запрашивается из 1С.

## 4. Процесс «перемещение между цехами»

Используется штатный документ 1С «Перемещение товаров» с доработкой.

### 4.1 Что уже есть в 1С и что меняется

В документе уже есть флаги **«Согласовано отправителем»** и **«Согласовано получателем»**
(с фиксацией пользователя), поставить каждый может только ответственный за соответствующий
склад, после обоих документ блокируется от правок; снять согласование может только
полноправный пользователь. Сейчас эти флаги **не влияют на проведение** — документ проводится
сразу. Доработка этапа 1: для перемещений между цехами документ **нельзя провести, пока
нет обоих подтверждений**. Пока их нет — товар числится у отправителя, у получателя его нет.

### 4.2 Жизненный цикл

```
POST /transfers (отправитель)  ──►  open, sender_confirmed = true
        │
        ├── PUT /transfers/{id} (любая сторона правит строки) ──► оба подтверждения сбрасываются
        │
        ├── POST /transfers/{id}/confirm (своя сторона) ──► когда обе стороны подтвердили ──► posted
        │
        └── DELETE /transfers/{id} (отправитель, пока не posted)
```

- Создаёт отправитель (начальник цеха-отправителя): цех-получатель, строки «номенклатура,
  количество». Создание автоматически ставит подтверждение отправителя.
- Получатель видит документ во входящих (`GET /transfers?direction=in`), проверяет.
  Согласен — `confirm`; не согласен — правит количество (`PUT`), подтверждения обеих сторон
  сбрасываются, документ возвращается отправителю на подтверждение. Цикл до согласия.
- Когда стоят оба подтверждения — 1С **проводит** документ: списание у отправителя, приход
  у получателя. Если на момент проведения остатка у отправителя не хватает — `confirm`
  вернёт ошибку `insufficient_stock`, подтверждение не ставится.
- После `posted` документ неизменяем. Отмена — только администратор в 1С.
- Отправитель не может передать больше, чем есть: 1С проверяет при `POST`/`PUT` по
  **доступному остатку** = остаток склада − количество в неподтверждённых исходящих
  перемещениях. Тот же доступный остаток отдаётся в `GET /workshops/{id}/stock`.

## 5. Общие правила API

### 5.1 Адрес и транспорт

- HTTP-сервис 1С, JSON, UTF-8. Базовый URL: `https://<сервер>/<база>/hs/lf/v1`.
  Тестовый адрес будет выдан отдельно после публикации dev-базы.
- Все ответы — `Content-Type: application/json; charset=utf-8`.

### 5.2 Авторизация

- `Authorization: Basic <base64(логин:пароль)>` — логин/пароль пользователя 1С.
- Неверные учётные данные — `401`. Нет прав на цех/операцию — `403` с `forbidden`.
- Какие цеха доступны пользователю — `GET /me`.

### 5.3 Идентификаторы, даты, числа

- `id` — GUID ссылки 1С, строка `"c9ab8ae1-c8b6-11e9-ba09-d48564791284"`.
- Даты — `"2026-09-13"`, дата-время — `"2026-09-13T14:30:00"` (местное время сервера,
  без зоны).
- Количества — числа с точкой, до 3 знаков. Единица измерения — базовая единица
  номенклатуры, отдаётся в справочнике (`unit`).

### 5.4 Идемпотентность

- `POST /shifts` идемпотентен по ключу (цех, дата, номер смены).
- `PUT` по определению идемпотентен (полная замена).
- Для `POST /transfers` и `POST .../close` приложение передаёт заголовок
  `Idempotency-Key: <uuid>`; повтор с тем же ключом возвращает результат первого вызова,
  а не создаёт дубль.

### 5.5 Версии и конфликты

- Каждый документ в ответах имеет `version` (строка). `PUT` и `POST .../confirm|close`
  принимают заголовок `If-Match: <version>`. Если документ изменили с другого устройства —
  `409 conflict` с актуальным документом в `details.current`. Приложение показывает
  расхождение и перечитывает.
- Без `If-Match` запись выполняется без проверки (для простых случаев допустимо).

### 5.6 Ошибки

Любая ошибка — HTTP 4xx/5xx и тело:

```json
{
  "ok": false,
  "error": {
    "code": "insufficient_stock",
    "message": "Недостаточно остатка: Пластикат ЭВА чёрный — доступно 120 кг, требуется 140 кг",
    "details": [
      { "item_id": "…", "item_name": "Пластикат ЭВА чёрный", "available": 120, "required": 140 }
    ]
  }
}
```

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `validation` | не заполнено обязательное, неверный формат, неизвестный `id` |
| 401 | — | не авторизован |
| 403 | `forbidden` | нет прав на цех/документ/операцию |
| 404 | `not_found` | документ не найден |
| 409 | `conflict` | версия устарела (`If-Match`) |
| 409 | `state` | операция невозможна в текущем статусе (PUT по закрытой смене и т.п.) |
| 422 | `insufficient_stock` | не хватает остатка — список позиций в `details` |
| 422 | `period_closed` | дата попадает в закрытый период |
| 422 | `posting_failed` | 1С отказала в проведении по другой причине — текст 1С в `message` |
| 500 | `internal` | ошибка сервера; `message` — для разработчика, пользователю показывать общий текст |

`message` всегда на русском и пригоден для показа пользователю как есть (кроме `internal`).

### 5.7 Кэш и частота запросов

- Контекст цеха (п. 6.3) — при входе и далее не чаще раза в 10–15 минут или по кнопке.
- Остатки — при открытии экрана перемещения/остатков.
- `PUT /shifts/{id}` — по факту изменения, допустима агрегация (раз в 10–30 с).
- История — по запросу пользователя, постранично.

## 6. Эндпоинты

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/ping` | проверка связи и версии |
| GET | `/me` | кто я, мои цеха, права |
| GET | `/workshops/{id}/context` | всё для работы смены одним запросом |
| GET | `/workshops/{id}/stock` | остатки склада цеха (доступные) |
| GET | `/shifts` | список смен цеха за период (история) |
| GET | `/shifts/{id}` | смена целиком |
| POST | `/shifts` | открыть смену |
| PUT | `/shifts/{id}` | сохранить состояние смены |
| POST | `/shifts/{id}/close` | закрыть смену (проведение) |
| POST | `/shifts/{id}/reopen` | переоткрыть (администратор) |
| GET | `/transfers` | входящие/исходящие перемещения цеха |
| GET | `/transfers/{id}` | перемещение целиком |
| POST | `/transfers` | создать перемещение |
| PUT | `/transfers/{id}` | изменить строки/комментарий |
| POST | `/transfers/{id}/confirm` | подтвердить своей стороной |
| DELETE | `/transfers/{id}` | удалить неподтверждённое |

### 6.1 `GET /ping`

```json
{ "ok": true, "api": "1.0", "config": "БП 3.0.74.76", "server_time": "2026-09-13T14:30:00" }
```

### 6.2 `GET /me`

```json
{
  "ok": true,
  "user": { "id": "…", "name": "Размела" },
  "is_admin": false,
  "workshops": [
    { "id": "dbb1a608-…", "code": "00-000004", "name": "Литейка ЭВА",
      "warehouse": { "id": "51e1765f-…", "name": "Литейный ЦЕХ ЭВА" } }
  ]
}
```

Пользователь без цехов получает пустой список — приложение показывает «нет доступа к цехам».

### 6.3 `GET /workshops/{id}/context?date=2026-09-13`

Один запрос при входе в цех. `date` необязательна (по умолчанию сегодня) — влияет на
состав действующих видов работ.

```json
{
  "ok": true,
  "workshop": { "id": "…", "code": "00-000004", "name": "Литейка ЭВА",
                "warehouse": { "id": "…", "name": "Литейный ЦЕХ ЭВА" } },
  "organization": { "id": "…", "name": "Хачатуров Арайр Владимирович ИП" },
  "employees": [
    { "id": "…", "code": "0000056", "name": "Иванова Анна Петровна", "position": "Литейщик",
      "default_work_type_id": "…" }
  ],
  "work_types": [
    { "id": "…", "code": "…", "name": "Литьё 6-парка", "unit": "пар", "is_downtime": false },
    { "id": "…", "code": "…", "name": "Простой", "unit": "ч", "is_downtime": true }
  ],
  "products": [
    { "id": "…", "code": "00-00001234", "article": "112/н", "name": "Сапоги женские ЭВА с манжетой",
      "unit": "пар", "spec": [ { "item_id": "…", "qty_per_unit": 0.42 } ] }
  ],
  "materials": [
    { "id": "…", "code": "…", "name": "Пластикат ЭВА чёрный", "unit": "кг" }
  ],
  "stock": [
    { "item_id": "…", "qty": 1250.5, "reserved": 0, "available": 1250.5 }
  ],
  "open_shifts": [
    { "id": "…", "number": "ЛФ-000123", "date": "2026-09-13", "shift_no": 1, "status": "open",
      "version": "AAAAAgAAAAA=" }
  ],
  "transfer_targets": [
    { "id": "…", "name": "Маркировка", "warehouse": { "id": "…", "name": "Склад Маркировка" } }
  ],
  "pending_incoming_transfers": 2
}
```

- `employees` — сотрудники, привязанные к цеху (регистр). `default_work_type_id` — вид
  работ по умолчанию, если задан.
- `work_types` — виды работ цеха на дату; `is_downtime` помечает «Простой».
- `products` — продукция цеха; `spec` — состав основной спецификации на единицу (для
  подсказки материалов в приложении; 1С при закрытии использует ту же спецификацию, если
  материалы не переданы).
- `materials` — объединение комплектующих всех спецификаций продукции цеха и позиций на
  остатке склада цеха.
- `stock` — остатки по всем позициям склада цеха (продукция и материалы вместе):
  `qty` — учётный остаток, `reserved` — в неподтверждённых исходящих перемещениях,
  `available = qty − reserved`.
- `transfer_targets` — цеха, в которые можно перемещать (все цеха с привязанным складом,
  кроме текущего).

### 6.4 `GET /workshops/{id}/stock`

То же, что `stock` в контексте, отдельным запросом:

```json
{ "ok": true, "as_of": "2026-09-13T14:30:00",
  "stock": [ { "item_id": "…", "name": "…", "unit": "пар", "qty": 640, "reserved": 120, "available": 520 } ] }
```

### 6.5 `GET /shifts?workshop={id}&from=2026-09-01&to=2026-09-13&status=closed&page=1&page_size=50`

Список смен цеха (шапки) за период, новые сверху.

```json
{ "ok": true, "total": 27, "page": 1, "page_size": 50,
  "items": [
    { "id": "…", "number": "ЛФ-000123", "date": "2026-09-12", "shift_no": 2, "status": "closed",
      "responsible": "Размела", "produced_total": 640, "defect_total": 12,
      "closed_at": "2026-09-12T22:40:00", "version": "…" }
  ] }
```

### 6.6 `GET /shifts/{id}`

Полный документ — та же структура, что в `PUT` (п. 6.8), плюс служебные поля
`id, number, status, version, responsible, created_at, closed_at, production_report`
(`production_report` — номер созданного ОПЗС, если смена закрыта).

### 6.7 `POST /shifts`

```json
{ "workshop_id": "…", "date": "2026-09-13", "shift_no": 1 }
```

Ответ `201` (или `200`, если такая смена уже открыта):

```json
{ "ok": true, "shift": { "id": "…", "number": "ЛФ-000124", "date": "2026-09-13", "shift_no": 1,
                         "status": "open", "version": "…", "workers": [], "outputs": [],
                         "products": [], "materials": [], "comment": "" } }
```

### 6.8 `PUT /shifts/{id}`

Полное состояние документа. Заголовок `If-Match: <version>` (рекомендуется).

```json
{
  "comment": "ночная, станок №2 простаивал 40 мин",
  "task_id": null,
  "workers": [
    { "employee_id": "…", "work_type_id": "…" }
  ],
  "outputs": [
    { "employee_id": "…", "work_type_id": "…", "product_id": "…", "qty": 96, "defect_qty": 2,
      "machine": "KCLKA 1", "note": "" },
    { "employee_id": "…", "work_type_id": "<id вида работ Простой>", "product_id": null, "qty": 0.67,
      "defect_qty": 0, "note": "нет сырья" }
  ],
  "products": [
    { "product_id": "…", "qty": 640, "defect_qty": 12 }
  ],
  "materials": [
    { "item_id": "…", "qty": 268.8 }
  ]
}
```

Правила:
- `workers` — состав смены; `work_type_id` необязателен.
- `outputs` — строки сделки. `product_id` обязателен для всех видов работ, кроме
  `is_downtime`. Количество — в единице вида работ (`unit`).
- `products` — итог выпуска; если пусто, 1С при закрытии посчитает как сумму `outputs.qty`
  по каждому продукту **по выпускающему виду работ** — но надёжнее, чтобы приложение
  передавало итог явно (решение за вами, см. вопрос В-3 в разделе 8).
- `materials` — по факту; пусто = по спецификации при закрытии.
- Все `*_id` проверяются на принадлежность цеху: чужой сотрудник/продукция — `validation`.

Ответ: `{ "ok": true, "version": "<новая>" }`.

### 6.9 `POST /shifts/{id}/close`

Заголовки `If-Match`, `Idempotency-Key`. Тело пустое или `{ "comment": "…" }`.

Успех:

```json
{ "ok": true, "shift": { "id": "…", "status": "closed", "closed_at": "…", "version": "…",
                         "production_report": { "id": "…", "number": "0000-012345", "date": "2026-09-13" } },
  "warnings": [ "Материалы заполнены по спецификации: 3 позиции" ] }
```

Ошибка — смена остаётся `open`, см. 5.6. Типичные: `insufficient_stock` (материалы на
складе цеха), `validation` (строка выработки без продукции; сотрудник без вида работ;
нет расценки на вид работ — `details` укажут строки), `period_closed`.

### 6.10 `POST /shifts/{id}/reopen`

Только администратор (`is_admin`). Тело `{ "reason": "…" }`. Ответ — документ со статусом `open`.

### 6.11 `GET /transfers?workshop={id}&direction=in|out|all&status=open|posted|all&from=&to=&page=&page_size=`

```json
{ "ok": true, "total": 5, "page": 1, "page_size": 50,
  "items": [
    { "id": "…", "number": "0000-000777", "date": "2026-09-13T11:20:00",
      "from": { "workshop_id": "…", "name": "Литейка ЭВА" },
      "to":   { "workshop_id": "…", "name": "Маркировка" },
      "status": "open",
      "sender_confirmed":   { "by": "Размела", "at": "2026-09-13T11:20:00" },
      "receiver_confirmed": null,
      "lines_count": 3, "qty_total": 640, "version": "…" }
  ] }
```

`status`: `open` — ждёт подтверждений; `posted` — подтверждено обеими сторонами и проведено.

### 6.12 `GET /transfers/{id}`

Шапка как в списке плюс `comment` и `lines`:

```json
"lines": [ { "item_id": "…", "name": "Сапоги женские ЭВА 112/н", "unit": "пар", "qty": 320 } ]
```

### 6.13 `POST /transfers`

Заголовок `Idempotency-Key`.

```json
{ "from_workshop_id": "…", "to_workshop_id": "…", "date": "2026-09-13",
  "comment": "", "lines": [ { "item_id": "…", "qty": 320 } ] }
```

Текущий пользователь должен быть ответственным за склад цеха-отправителя. Создание ставит
`sender_confirmed`. Проверка доступного остатка по каждой строке — иначе `insufficient_stock`.
Ответ `201` — документ как в 6.12.

### 6.14 `PUT /transfers/{id}`

`{ "comment": "…", "lines": [ … ] }` — полная замена строк. Допустимо любой из двух сторон
пока `status = open`. **Сбрасывает оба подтверждения.** Проверка доступного остатка
отправителя. Ответ — документ.

### 6.15 `POST /transfers/{id}/confirm`

Заголовок `If-Match`. Тело пустое. 1С определяет сторону по пользователю: ответственный за
склад отправителя ставит `sender_confirmed`, за склад получателя — `receiver_confirmed`
(если пользователь отвечает за оба — `{ "side": "sender" | "receiver" }` обязателен).
Когда оба подтверждения стоят — документ проводится. Ошибка проведения (обычно
`insufficient_stock` у отправителя на момент проведения) — подтверждение не ставится.
Ответ — документ.

### 6.16 `DELETE /transfers/{id}`

Только отправитель, только `status = open`. Ответ `{ "ok": true }`.

## 8. Что нужно решить и подготовить на стороне фабрики

**Решения (на созвоне не закрыты):**

- **В-1. Материалы.** По данным 1С контроль отрицательных остатков включён на сырьевых
  складах цехов («материалы для кроя», «штробель», «Пластикат 6», «ПВХ Игорь», «Литейный
  ЦЕХ ЭВА»). Значит закрытие смены упадёт, если материала на складе цеха нет. Нужен ответ
  бухгалтерии: материалы к моменту смены уже на складе цеха, или передаются задним числом?
  От этого зависит, списываем при закрытии смены или нет.
- **В-2. Один склад на цех.** Сегодня в ОПЗС у цеха два склада: с одного списываются
  материалы, **на другой — склад следующего цеха — сразу приходуется продукция**
  (Крой: «материалы для кроя» → «крой (рубка)»; Штробель: «штробель (Швейное
  производство)» → «Заготовки для обшива»; Литейка ЭВА: «Пластикат 6» → «Литейный ЦЕХ
  ЭВА»; Упаковка ЭВА: «Упаковка (Размела)» → «Готовая продукция (Размела)»; Клеевая: «Китай
  (Коля)» → «Склад Маркировка» и т.д.). В новой модели продукция приходуется на **склад
  своего цеха**, а дальше идёт перемещением с подтверждением получателя. Нужно утвердить
  таблицу «цех → единственный склад» (предложение подготовлю отдельно по данным базы) и
  подтвердить, что бухгалтерию устраивает появление перемещений между цехами вместо
  прямого прихода на следующий склад.
- **В-3. Итог выпуска.** Считает ли приложение `products` из выработки (по выпускающему
  виду работ) или начальник цеха вводит итог отдельно? Рекомендую вводить отдельно —
  выработка по операциям (обрезка, упаковка) не равна количеству готовых пар.
- **В-4. Смены.** «День/ночь» или «первая/вторая» — в API это просто `shift_no` 1/2,
  названия — дело приложения.
- **В-5. Брак.** В 1С брак фиксируется количеством в продукции и штрафом по виду работ;
  на склад отдельным сортом не приходуется. Если нужен учёт брака на остатках — отдельное
  решение.

**Данные:**

- Список начальников цехов и Ромы: ФИО, цех, желаемый логин — заведём пользователей 1С.
- Подтверждённая таблица цех → склад (В-2).
- Привязка сотрудников к цехам — первичное заполнение регистра (из `employees.xlsx`
  приложения можно взять как черновик).
- Вид работ «Простой» для каждого цеха, если простой нужно фиксировать.

## 9. Тестовая среда и этапность

1. Документ согласовываем → фиксируем v1.0.
2. 1С: новый документ, регистры привязок, HTTP-сервис, доработка перемещения — на dev-базе
   (копия рабочей). Тестовые пользователи `цех_литейка`, `цех_крой`, … — выдам вместе с URL.
3. Приложение параллельно переводит слой данных на этот контракт; до готовности сервиса —
   на заглушках по примерам из раздела 6.
4. Совместный прогон на dev-базе: открыть смену → выработка → закрыть → ОПЗС в 1С;
   перемещение → подтверждение → остатки.
5. Публикация на рабочей базе — отдельный шаг (веб-сервер, HTTPS, пользователи).

Этап 2 (заказы, задания на смену, склад ГП) проектируется отдельно; в контракте под него
зарезервированы `task_id` в смене и `transfer_targets` в контексте.
